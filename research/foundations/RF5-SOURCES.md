# RF5 Sources — Time, Ordering, Concurrency and Causality

## S1 — Lamport: Time, Clocks, and the Ordering of Events

Leslie Lamport, **Time, Clocks, and the Ordering of Events in a Distributed
System**, Communications of the ACM 21(7), 1978.

Canonical author record: Microsoft Research.

RF5 use:

- happened-before as a partial order generated by local process order, message
  send→receive and transitivity;
- concurrent events are incomparable under this relation;
- logical clocks can respect causal order;
- a total order can extend the partial order without turning all ordered pairs into causal
  pairs;
- provides the central anti-collapse between physical/wall-clock order and logical causal
  order.

## S2 — Chandy & Lamport: Distributed Snapshots

K. Mani Chandy and Leslie Lamport, **Distributed Snapshots: Determining Global States of
a Distributed System**, ACM TOCS 3(1), 1985.

Canonical author record: Microsoft Research.

RF5 use:

- meaningful global state can be captured as a consistent distributed snapshot without
  stopping the whole system or requiring one perfectly synchronized wall-clock instant;
- process and channel states jointly matter;
- supports `ConsistentGlobalSnapshot != SimultaneousWallClockRead`.

## S3 — POSIX.1-2024: CLOCK_REALTIME and CLOCK_MONOTONIC

The Open Group / IEEE, **POSIX.1-2024 System Interfaces / Clocks and Timers**.

Canonical source: The Open Group Base Specifications Issue 8 / IEEE Std 1003.1-2024.

RF5 use:

- `CLOCK_REALTIME` is the system-wide realtime clock;
- `CLOCK_MONOTONIC` cannot be set with `clock_settime` and cannot jump backwards;
- POSIX rationale explains why monotonic clocks are appropriate for relative/elapsed
  waits when realtime clock correction can distort waiting behavior;
- supports the separation between durable civil timestamps and local duration/deadline
  control.

## S4 — Herlihy & Wing: Linearizability

Maurice Herlihy and Jeannette M. Wing, **Linearizability: A Correctness Condition for
Concurrent Objects**, ACM TOPLAS 12(3), 1990.

Canonical author record: Jeannette Wing publication archive, Carnegie Mellon University.

RF5 use:

- concurrent operations can be mapped to a legal sequential history;
- non-overlapping operation real-time precedence must be preserved;
- overlapping operations may linearize in an order permitted by object semantics;
- supports `InvocationOrder != LinearizationOrder != ResponseOrder` and distinguishes
  linearizability from weaker sequential-equivalence notions.

## S5 — PostgreSQL Serializable isolation

PostgreSQL Global Development Group, **Transaction Isolation / SERIALIZABLE** current
documentation.

Canonical source: postgresql.org documentation.

RF5 use:

- physically concurrent transactions can commit only when their combined effect is
  consistent with some serial one-at-a-time execution;
- serialization anomalies can force rollback/retry;
- supports `Serializable != PhysicallySequential` and separation of serialization order
  from wall-clock start order.

## S6 — SQLite isolation/concurrency

SQLite project, **Isolation In SQLite**.

Canonical source: sqlite.org.

RF5 use:

- SQLite serializes writers so only one writer proceeds at a time under ordinary
  operation;
- demonstrates a concrete concurrency-control mechanism that is scoped to the database
  substrate rather than a global ordering ontology for all higher operations.

## S7 — Current Ordivon Runtime as empirical source

RF5 audits current source/test behavior.

### Per-Job event order

`append_event` allocates:

```text
SELECT COALESCE(MAX(event_sequence),0)+1
FROM job_events
WHERE job_id=?
```

inside the Registry transaction.

RF5 therefore treats `event_sequence` as a per-Job durable Registry append/serialization
order rather than global, physical or causal chronology.

### Observation timestamps

`job_events` also stores `observed_at_ms`, supplied from the evidence/transition context.
This can represent evidence time distinct from Registry append order and can therefore
legitimately disagree with `event_sequence` under delayed recovery/observation.

### Clock split

Current Core uses Rust `Instant` for local waits/deadlines such as startup grace,
`task.observe(waitMs)` and short provider polling, while persistent records use Unix
system timestamps. RF5 classifies those as monotonic control time versus durable
wall/evidence time.

### Concurrent admission

The `simultaneous_same_key_creates_one_job_and_one_attempt` test races two callers and
proves transactional idempotency creates one Job/reservation. RF5 treats this as
concurrent invocation plus serialized durable admission, not caller-arrival chronology.

### Diagnostic latency

Inspection derives admission→dispatch, dispatch→Runner, Runner→terminal and other latency
projections from persisted event `observed_at_ms`. RF5 treats them as useful wall/evidence
timeline diagnostics, not exact monotonic/causal latency truth.

## Source discipline

Later rounds should preserve:

```text
clock reading != physical time
wall time != monotonic duration
logical totalization != discovered total causality
happens-before != complete metaphysical/physical causation
serialization != physical sequential execution
linearization order != invocation/response order by default
consistent snapshot != simultaneous timestamp equality
Registry event_sequence remains scoped Runtime history order
external provider timestamps/orders require provider clock/protocol semantics
```
