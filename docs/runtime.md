# Ordivon Runtime Model

## Purpose

A participant, Agent, or Host forms and admits work. Ordivon Runtime executes it, owns the resulting process tree, records non-reconstructable execution truth, and reconciles that truth after interruption.

## Boundaries

Runtime owns physical operation admission, process-tree supervision, durable execution identity, bounded result evidence, cancellation, reconciliation, and Workspace lifecycle. Git, SQLite, systemd/cgroups, digest-bound files, and generated MCP schemas remain the strongest owners of their respective facts. Host and participants retain semantic completion, purpose, and commitment judgments.

### Component responsibility matrix

| Component | Owns | Explicitly does not own |
| --- | --- | --- |
| Runtime | Workspace lifecycle, physical operation admission, Jobs, Attempts, process trees, bounded Artifacts, cancellation, reconciliation, and enforceable effect receipts | Task/Goal semantics, Assignment or Run policy, Provider execution, domain verification, or product policy |
| Host | durable Task continuity, Journal/CAS, generic extension admission, commitment identities, verification records, and Task outcomes | Harness-specific Run schemas, Provider loops, physical execution truth, or domain-world truth |
| Harness | Task Attempt and Assignment semantics, Agent Runs, Provider adapters, model–Tool loops, Tool-step checkpoints, Run recovery, and completion proposals | generic Task persistence, another database or scheduler, Runtime supervision, promoted protocol, or final domain authority |

## Data flow

```text
request
→ exact Git Workspace
→ transactional admission
→ Job + Attempt + reservation
→ immutable runner bundle
→ systemd transient unit and cgroup
→ bounded result and Artifacts
→ reconciliation
```

A Workspace isolates the checked-out code tree and Git state. It does not reduce the installed service user's host authority.

## Truth owners

| Fact | Owner |
| --- | --- |
| Repository history, diff, rollback, Workspace identity | Git |
| Request identity, Job, Attempt, reservation, cancellation, resolution | SQLite Registry |
| Running process tree and termination | systemd and cgroup |
| Result and Artifact bytes | Digest-bound files |
| Public Tool contract | MCP schema generated by the server |
| Current deployment and health | live service, configuration, Git, and Runtime inspection |

Information reconstructable from these owners should not be persisted as a second proof system.

## Components

```text
Principal
└── submits an idempotent request
    └── identifies one Job in one Workspace
        └── owns an Attempt
            ├── consumes a concurrency reservation
            ├── binds an immutable runner bundle
            ├── owns one systemd unit and process tree
            └── produces a terminal Result and Artifacts
```

The Job expresses desired state and final resolution. The Attempt expresses one bounded execution history. Conditions and append-only events preserve the evidence needed to understand incomplete or corrected state without inventing another execution path.

## Irreducible invariants

- Repeating the same authenticated client request is idempotent.
- A candidate Agent action is not physical commitment until durably admitted.
- One Attempt crosses the physical dispatch boundary at most once.
- An ambiguous dispatch is never speculatively repeated.
- A newly admitted Job binds the exact Runtime-owned execution provider contract and executable digest; provider drift before dispatch fails closed instead of changing the machinery that realizes an already committed operation.
- One Attempt owns the complete command process tree through one cgroup.
- After that process tree is proven gone, a complete identity-bound Runner Result is terminal execution truth.
- Execution truth is not automatically an external-effect receipt or semantic-completion proof.
- Work that cannot be proven running or terminal becomes `lost` or `orphaned`; it is not guessed successful, guessed failed, or automatically redispatched.

The complete Agent Effect Commit Kernel contract, current proof boundary, costs, and implementation gate are in [`effect-kernel.md`](effect-kernel.md). Other exact limits, states, fields, transitions, Tool arguments, and configuration belong to source, migrations, tests, generated schemas, and the live Runtime.

## Failure modes

Runtime preserves ambiguous dispatch, missing terminal evidence, residual process ownership, stale source commitment, capacity exhaustion, and cancellation races as explicit failure or recovery states. It must not guess success, hide uncertainty, or redispatch an opaque operation merely because a response was lost.

## Reconciliation

Reconciliation compares Registry state with runner evidence and systemd/cgroup reality. It runs during startup recovery, configured background maintenance, execution admission for the relevant Workspace, explicit maintenance calls, and exact-Job `task.observe`. Projection-only listing/get paths do not reconcile or dispatch work. One Job's recoverable inconsistency must not expand into a service-wide failure.

## Terminal supervision evidence

Every terminal Attempt registers `terminal-evidence-<digest>.json` as a `terminal_evidence` Artifact. The evidence binds the durable Job and Attempt to the committed Workspace, source revision, execution profile, optional foreign references, explicit Host Dependency prerequisite commitments when present, exact command, systemd unit, invocation, cgroup, PID identity, Runner-start digest, terminal reason, and the other terminal Artifact identities. It projects three orthogonal facts instead of expanding the Job state machine:

- `executionDisposition`: the committed Attempt terminal state;
- `deliveryDisposition`: whether the terminal result was committed, is unknown, or still requires reconciliation;
- `processTreeDisposition`: `terminal_clean`, `unexpected_residual`, or `unknown`.

Runtime prefers the recursive cgroup-v2 `cgroup.events: populated` fact and falls back to direct `cgroup.procs` membership only when the events file is unavailable. The evidence remains an Artifact consumed through `task.observe` and `artifact.read`; Runtime does not add a parallel evidence Tool or foreign-reference database. Foreign references are immutable opaque inputs in the Execution Plan and therefore participate in request identity, replay conflict detection, and the plan digest; Runtime does not impose an arbitrary count ceiling on them.

### Host correlation convention

Harness-originated execution uses opaque `ordivon.host` foreign references for the Host Task, Host Task Attempt, Assignment, and Harness Run. The Host places Task revision in the `task` generation, Assignment generation in the `assignment` generation, and binds each reference to its Host-owned digest. Runtime preserves these values exactly; it does not interpret Assignment validity, Harness capability, or Host Task state.

Exact `clientRequestId` replay with the same execution request and references returns the original Runtime Job. Changing Assignment generation or digest under that request identity is an idempotency conflict, so stale work cannot masquerade as replay. A recovery caller locates the original Job with the exact `clientRequestId` and reads its immutable Execution Plan or terminal-evidence Artifact. Runtime success remains physical execution evidence; semantic CompletionProposal adjudication and TaskOutcome commitment remain Host-owned.

The public `task.get`, `task.observe`, `task.list`, and `task.cancel` names remain ordinary Runtime Job Tools rather than MCP Tasks extension methods. `task.get` and `task.list` are projection-only reads; `task.observe` may reconcile or dispatch the exact already-admitted Job; `task.cancel` persists stop intent and reconciles the owned process tree. Public prose distinguishes Host Task Attempt, Harness Run, Runtime Job, and Runtime Attempt; Runtime adds no Host-specific enum, state table, query service, or semantic-completion authority. Agent-facing Job projections expose `semanticCompletionEvaluated=false` only as an explicit negative boundary so execution success cannot be mistaken for Task or domain completion.

A verified terminal result can defeat a later cancellation race because observed completion is stronger evidence than delayed intent. An identity-uncertain Attempt remains `orphaned` and retains its reservation while its recorded unit, process identity, or cgroup may still own a live process tree. When all three are proven absent, reconciliation converges it to `lost`, `timed_out`, or `cancelled` according to persisted intent and releases the reservation atomically. A late identity-bound runner Result still takes precedence when available.

## Workspace source commitment

A `clientRequestId` binds the stable operation request separately from the observed Workspace. Replaying the same request returns the original durable Job without resolving the current Workspace again, including after that Workspace has changed or closed. The initial admission then binds a digest of the Workspace's Git source state: current `HEAD`, the semantic Git index including index flags, every tracked path's actual file or symlink bytes and mode, recursively initialized submodule source state, and sorted nonignored untracked files or symlinks. Ignored caches and build outputs are deliberately excluded. The digest participates in operation identity and is checked again by the Runner immediately before the target executable is spawned.

The Runtime also rejects `workspace.mutate` and `workspace.patch` while an active or held Job owns that Workspace. This prevents Ordivon-mediated mutations from changing the committed source world during execution. `workspace.patch` adds stable request identity and a durable receipt around the same digest-guarded physical text mutation; it does not create a second Workspace or Job lifecycle. The cost is deliberate: editing and execution that must overlap use separate Workspaces rather than weakening one Job's source precondition. `workspace.diff` independently projects the Git path status into sorted changed, modified, added, deleted, renamed, and untracked sets while retaining the bounded patch text. This keeps physical Git classification in Runtime and lets Host compare an exact planned file set without parsing human-oriented diff headers.

This is a trusted-local pre-spawn commitment, not an immutable filesystem snapshot. A host process with the same authority can still write directly outside the Runtime, including in the interval after Runner validation, and a running command may intentionally modify its own Workspace. Ignored files, wall-clock time, network state, and other ambient dependencies are not included. Target processes do not inherit the Runtime service environment: the Runtime binds configured `ORDIVON_EXEC_PATH` and `ORDIVON_EXEC_HOME` values plus a fixed locale, temporary directory, and explicit cache paths into the committed execution plan, then overlays only the request's explicit environment. In `trusted_local`, package-download caches are global to the Runtime, while compiled build targets are Workspace-scoped. Detached Workspaces therefore reuse downloaded dependencies without writing compiler artifacts into one another's target directory. This boundary is deliberate: cross-checkout compiled-artifact reuse belongs in a content-addressed compiler cache such as a future `sccache`-style layer, not in one shared mutable Cargo `target/`. `contained_local` keeps both package/tooling caches and build targets Workspace-scoped to avoid widening its reduced authority. Stronger immutability would require a separate snapshot or isolation design and its merge-back cost; it is not claimed here.

Workspace file observation has a separate path-authority boundary from source-state commitment. `workspace.read` and `workspace.content` open the Workspace root with `O_NOFOLLOW`, then use Linux `openat2` relative to that directory descriptor with `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` and a no-follow final component. Metadata, bounded byte reads, digests, UTF-8 decoding, and media checks operate on that already-opened file descriptor rather than reopening a previously canonicalized pathname. This closes the demonstrated race where a same-authority process could replace a checked file with a symlink between `canonicalize` and `read`. Relative parent symlinks remain usable only when kernel resolution keeps them beneath the Workspace root. This hardening is currently a **read/observation** invariant; it does not claim that every Workspace write/mutation pathname has been converted to descriptor-relative mutation semantics.

## Execution authority profiles

`workspace.exec` and `workspace.execPlan` accept `executionProfile` with two values. `workspace.execBound` does not expose this choice: immutable inputs structurally require `contained_local`.

- `trusted_local` is the canonical owner-trusted profile. It grants the installed service user's local authority without adding a central approval layer.
- `contained_local` is explicit and never silently falls back. Runtime uses the same systemd transient-unit supervisor, but sets a private network, removes effective and ambient capabilities, enables no-new-privileges, restricts namespaces and address families, makes the base filesystem read-only, hides `/root`, `/home`, `/run`, and `/var`, and bind-mounts back only the exact Runner, Git common directory, Workspace, Attempt bundle, and Runtime-created cache paths required by the committed plan. The Runner receives a fixed environment allowlist plus `GIT_OPTIONAL_LOCKS=0`; request environment is passed only to the target process through the durable Runner request.

This profile protects accidental credential and host-state access by local engineering workloads. It deliberately does not claim kernel-grade isolation against hostile same-host code, filesystem confidentiality outside the hidden state hierarchies, controlled egress, or disposable-machine semantics. Those belong to Edge or another external isolation owner. Dynamic users, bubblewrap, generic proxying, and policy-specific approval state are not part of contained v1 because they would duplicate supervision or introduce ownership and mount-composition costs without a demonstrated workload requirement.

## Execution budgets

Time and output bounds are always concrete in the durable Execution Plan. `ORDIVON_MAX_RUNTIME_MS` and `ORDIVON_MAX_OUTPUT_BYTES` define operator-owned server ceilings; production may keep conservative values while another installation may deliberately choose larger ones. Agent-facing `workspace.exec`, `workspace.execPlan`, and `workspace.execBound` may omit the Job timeout, retained stdout/stderr limits, and step-local timeouts. Omission delegates only that mechanical constraint to Runtime: proposal identity preserves the omission, first admission resolves it from current operator policy, and the resulting concrete values are frozen into the Execution Plan. Explicit values are never silently clamped; a new admission whose explicit value exceeds current policy is rejected.

Current policy gates only new admission. Runtime performs idempotent existing-Job lookup before applying the current ceilings, so replay after a policy change returns the original Job and its original effective limits rather than recomputing or rejecting historical truth. `workspace.exec`, `workspace.execPlan`, and `workspace.execBound` responses plus `task.observe` project those durable values as `effectiveLimits`. A structured plan's Job-wide timeout is one shared overall deadline; step-local timeouts are independent upper bounds and their arithmetic sum is not a Runtime law. The MCP adapter retains the previous fully explicit request shape and legacy request identity path; using any new optional/delegated limit semantics selects the proposal identity path.

Runtime no longer adds a separate 24-hour/64-MiB product law. A caller may also commit optional positive physical budgets for memory, process count, and CPU quota. These values participate in the operation Digest and are applied by systemd to the Attempt cgroup through `MemoryMax=`, `TasksMax=`, and `CPUQuota=`. Runtime validates representability and positivity, while the operator and systemd/kernel own the actual resource policy. An empty budget is omitted from canonical serialization so requests admitted before this contract remain idempotently replayable.

Budgets constrain physical consumption; they are not a scheduler, priority system, sandbox, or approval policy. The trusted-local authority model remains unchanged.

## Execution provider commitment

First admission commits the Runtime-owned machinery that will cross the physical dispatch boundary. `local_linux` binds the validated Runtime Runner contract plus its executable SHA-256. `windows_native` binds the Windows launcher contract, launcher executable SHA-256, and configured WSL distribution used for path projection. The snapshot is stored in an additive Job-owned Registry table and its digest is bound into the Job's `runtime-operation-v4` identity; the strict `RuntimeExecutionPlan` JSON shape remains unchanged so the receipt-bound previous binary can still decode retained plans.

Dispatch re-observes the configured provider before bundle/target launch. An exact mismatch terminates the committed Attempt with `EXECUTION_PROVIDER_PRECONDITION_DRIFT` before a systemd unit or Windows child is created. For current provider-bound Linux Jobs, P3 additionally requires the running Runner to hash its actual `/proc/self/exe` into `runner-start.json`; Core requires that digest to equal the committed `local_linux_runner_v1` provider and, while systemd `MainPID` is still alive, independently hashes `/proc/<MainPID>/exe` and requires all three identities to agree. This closes the distinction between “the configured Runner path hashed correctly before launch” and “this is the image systemd actually started” without changing historical operation identity. A missing, extra, digest-mismatched, or contract-invalid side record is Registry corruption rather than a reason to reinterpret a provider-bound Job as historical. Jobs admitted before this contract have no provider commitment marker and preserve their historical behavior. Exact request replay is resolved before the current provider is inspected, so a terminal or already committed Job never becomes unreplayable merely because Runtime itself was upgraded later.

This commitment is deliberately narrow. It proves continuity of Runtime's own Linux Runner or Windows launcher and their declared dispatch contract; it does not by itself freeze shared libraries, kernel behavior, compiler/package closure, network responses, wall clock, external services, or the semantic contract of an arbitrary target command. P2 physically falsified one part of that boundary: the same dynamically linked target executable, with the same executable SHA-256 and the same prior operation identity, produced `ENV_V1` and `ENV_V2` after only its runtime-loaded shared library changed. Runtime therefore supports explicit `hostDependencies` for trusted-local Linux Jobs: each binding is an Agent-declared absolute regular non-symlink host file plus expected SHA-256, validated on new admission, stored as additive Job side truth, bound into `runtime-operation-v6`, and checked again before bundle dispatch. Empty bindings retain historical request and operation identities.

P3 then physically falsified the remaining pre-spawn claim. A real Runtime target passed every P2 check, printed `READY`, waited, and only afterward called `dlopen()` on a declared Host Dependency. Replacing that path between `READY` and `dlopen()` made the target consume V2 while P2 terminal evidence still named the committed V1 digest. Runner now establishes Linux inotify path/topology witnesses **before** its final Host Dependency digest validation, drains them before spawn, and keeps them active through the complete Attempt. Relevant file or ancestor-component write, metadata change, create/delete, rename/move, unmount/ignored watch, or queue overflow fails the Attempt as `HOST_DEPENDENCY_RUNTIME_DRIFT`; a terminal evidence record may state `hostDependencyContinuity=no_runtime_path_drift_observed` only when the Runner execution loop completed without such a witnessed event. This is a path-continuity witness, not a claim that the dependency was made immutable or that every possible consumption mechanism was intercepted.

The same validation-to-path-use problem exists for target executables. Runner establishes an executable path/topology witness before its final canonicalize/hash and keeps that witness active for the entire step. Runtime deliberately continues launching the original pathname: P3 proved that sealed memfd execution can force exact bytes but changes legitimate shebang `__file__`/`sys.argv[0]` and ELF `/proc/self/exe` semantics. A runtime executable pathname change therefore fails as `EXECUTABLE_RUNTIME_DRIFT` instead of silently changing execution, while normal target pathname semantics remain unchanged.

Host Dependency commitments are not an environment-image system and not automatic dependency discovery. Runtime cannot honestly infer every ELF loader edge, `dlopen`, Python/Node module, GPU driver, kernel facility, network service, or other ambient prerequisite. The Agent/domain declares prerequisites it knows materially define the physical action; Runtime makes those declarations identity-bound and witnesses ordinary Linux filesystem-path drift during the Attempt. P3 also physically rejected a single-file `BindReadOnlyPaths=snapshot:original` fix: replacing the parent-directory entry still made a delayed `dlopen()` resolve the new file. The current contract therefore says exactly what it can prove—no relevant path/topology drift was observed—not that the bytes were globally frozen. Same-authority mount-namespace intervention, undeclared dependencies, and non-filesystem ambient state remain outside this claim. `contained_local` and Windows-native execution do not support Host Dependency commitments in this version.

## Windows-native execution target

`executionTarget` is orthogonal to `executionProfile`. `local_linux` remains the default and preserves the historical request-identity canonical form; `windows_native` is a distinct operation identity and is available only when the Runtime instance has explicit Windows provider configuration. It is not a third authority profile. R-W3 still admits one `trusted_local` Windows command at a time; structured multi-step plans and `workspace.execBound` immutable-input admission remain Linux-only. Windows-native requests additionally expose `windowsAuthority=limited|elevated`; `limited` is the default. This field is target-specific requested authority, not an `ExecutionProfile`. Default limited requests retain the R-W2 canonical operation identity, while explicit `elevated` participates in operation/proposal identity and therefore cannot alias an existing limited Job.

On a configured WSL/Windows node, Runtime keeps the existing durable Job/Attempt lifecycle and uses systemd only as the **outer WSL launcher supervisor**. That supervisor is invoked with `systemd-run --expand-environment=no`: Agent-authored Windows argv is execution truth, so `$VAR` and `${VAR}` must not be rewritten from systemd's manager environment before the Windows launcher receives them. The repository-owned [`../platform/windows/Ordivon.WindowsJobLauncher.cs`](../platform/windows/Ordivon.WindowsJobLauncher.cs) creates a named Windows Job Object, creates the exact target process suspended, assigns and verifies Job membership before resume, captures bounded stdout/stderr, enforces the committed timeout, and closes/terminates the whole Job before terminal evidence is accepted. The actual Windows child identity is not copied into the Linux `mainPid`: `windows-start.json` separately binds the Runtime Job/Attempt and launch-token digest to the Windows Job name, Windows PID, process creation FILETIME, exact image path, and image SHA-256 digest, and is retained as a `windows_start` Artifact.

Windows target commands do not inherit the Runtime Linux service environment or an ambient WSL-to-Windows process environment. On first admission, the exact configured launcher selects and proves the token class requested by `windowsAuthority`, asks Windows for that token's native user/machine profile environment with inheritance disabled, projects only Runtime's mechanical allowlist, and returns that bounded context to Core. Runtime validates the token evidence, freezes the allowlisted baseline plus the Agent's explicit `env` overlay into `RuntimeExecutionPlan`, and records a `WindowsExecutionContext` naming the effective token class, user SID, and environment-source contract. Exact replay returns the committed Job without re-reading the launcher, token, or current Windows environment. `PNPM_HOME`, `OneDrive`, `WSL_DISTRO_NAME`, `PSModulePath`, and other non-allowlisted ambient variables are not promoted merely because Windows exposes them. PowerShell is not inserted into the execution path.

The default Windows execution authority is deliberately narrower than the ambient WSL interop launcher authority. On the verified workstation, WSL launches the provider with a Full/High administrator token. The linked UAC token exposed through WSL is only an Identification-level impersonation token and cannot be used as a primary execution token. For `windowsAuthority=limited`, Runtime therefore derives a Windows-native limited primary token with `CreateRestrictedToken(..., LUA_TOKEN)`, lowers its mandatory integrity label only when necessary to Medium, and fails closed unless the effective token is Primary, non-elevated, no higher than Medium integrity, the same user SID, and Administrators is not enabled; the observed LUA-derived form requires Administrators to be deny-only.

`windowsAuthority=elevated` is explicit selection of authority that the configured provider **already possesses**; Runtime does not invoke UAC UI, follow the unusable linked token, or acquire new machine authority. Admission and dispatch accept elevated execution only when the current provider token itself proves Primary, elevated, High-or-higher integrity, Administrators enabled, and the same effective user SID. The launcher uses `CreateProcessAsUserW` for both authority classes. `RuntimeExecutionPlan.windowsAuthority` records requested authority while `WindowsExecutionContext.tokenClass` records effective authority; `windows-start.json` independently records effective token selection, SID, token/elevation type, elevation bit, integrity RID, restricted-token observation, and Administrators group attributes. Runtime requires requested and effective authority to agree before terminal commit. Physical acceptance also contrasts a bounded HKLM effect: limited execution is denied, explicit elevated execution succeeds and removes the temporary key before exit.

The provider facts are operator-owned rather than Agent-authored: `ORDIVON_WINDOWS_LAUNCHER_PATH` names the exact WSL-visible Windows launcher executable and `ORDIVON_WINDOWS_WSL_DISTRIBUTION` names the WSL distribution used to project Workspace and Attempt-bundle paths through `\\wsl.localhost`. Both must be configured together. Windows executables must be exact files beneath a WSL-mounted Windows drive such as `/mnt/c/...`; Runtime hashes that file before admission and verifies the Windows image identity against the committed digest. Workspace and Attempt authority are not copied to a second Windows workspace: Win32 accesses the existing WSL paths through the explicit UNC projection.

The launcher applies native Job limits for committed job memory, active process count, and CPU rate. `--cpu-quota-percent` uses Runtime's one-CPU-equivalent interpretation: Windows Job CPU rate is a share of the whole Windows machine, so the launcher converts the requested quota to `floor(cpuQuotaPercent * 100 / logicalProcessors)`, bounded to `1..10000`. Windows `ActiveProcessLimit` and `JobMemoryLimit` are not declared byte-for-byte semantic equivalents of Linux cgroup `TasksMax` and `MemoryMax`; they are target-native enforcement of the same requested budget dimensions with target-specific accounting.

R-W4 adds one more physical invariant without adding Agent-authored operation semantics: every Runtime-mode Windows launcher acquires a Windows Power Request of type `SystemRequired` before the native child is started. The reason string is `Ordivon Runtime Attempt <attemptId>`, binding external observation to the physical Attempt. `windows-start.json` records `powerRequestType=system_required` and `powerRequestAcquired=true`, and Core fails closed if that acquisition evidence is missing. The lease is owned by the launcher handle/process, not by a new durable power manager. On normal completion or launcher-managed timeout the launcher clears and closes the lease before publishing `result.json`; cancellation/crash process teardown closes the handle as an operating-system cleanup boundary. Exact replay of a terminal Job does not start the launcher and therefore cannot reacquire the lease. `powercfg /requests` is used only as external acceptance observation, never as Runtime authority.

The selected request is intentionally `SystemRequired`, not a global power-plan mutation or display/away-mode request. Its purpose is to prevent idle-triggered system sleep while a Windows Attempt has active physical work. User-initiated sleep/lid behavior remains owned by Windows/Workstation policy rather than being overridden by Runtime. Physical falsifiers prove the request is externally visible while both limited and elevated cancel fixtures are running, disappears immediately after explicit clear while a holder remains alive, and also disappears after forced holder termination without an explicit clear. Success, timeout, cancellation, and terminal replay all end with no matching Attempt-scoped request.

R-W5 closes the WSL/connector recovery boundary without adding a second Windows scheduler or Registry identity. Reconstructing `Runtime` against the same Registry while the outer launcher is still alive reattaches the exact Job/Attempt and preserves the active Power Request; the reconstructed Runtime can cancel the original Attempt and no duplicate dispatch occurs. If the launcher lineage itself disappears, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` makes that a physical execution-failure boundary rather than a surviving native continuation case: the Windows process tree and Power Request disappear. For a natural `windows_native` Attempt with no result, a missing supervisor unit and dead recorded launcher process therefore converge to `failed` with `WINDOWS_LAUNCHER_LINEAGE_GONE`; Linux, explicit cancellation, and deadline semantics keep the generic supervisor classifier.

Two real `wsl --terminate archlinux`/restart falsifiers exposed an important substrate fact: `/proc/sys/kernel/random/boot_id` remained unchanged across distro termination and restart on this WSL2 machine, so Runtime must not interpret the Linux kernel boot ID as a WSL distro-instance identity. Before reconciliation, the old Attempt still existed as `running` with an active reservation while its systemd unit was `not-found`, MainPID was zero, and Windows-side observation proved marker processes and the Attempt Power Request were gone. The generic pre-R-W5 rule classified this as `lost`; the target-aware rule was then physically re-run through a second real distro termination and converged the same condition to `failed`, released the reservation, and exact replay returned the same terminal Job/Attempt without redispatch. No new Windows child Registry columns were required.

User-initiated host suspend/lid behavior remains a Workstation/Windows policy boundary rather than an R-W5 continuation promise. `SystemRequired` intentionally protects active work from idle-triggered sleep; Runtime does not globally prevent explicit host sleep. Long Paths admission evidence remains a later target layer. Ambiguous effects are never automatically redispatched.

The repeatable equipment proof is `scripts/windows-job-launcher-acceptance.py`; it verifies the legacy Job Object mechanics plus both limited and elevated runtime-context selection, requiring the same SID and the same bounded baseline environment while authority evidence changes. The ordinary Runtime-level proof is the ignored `runtime_windows_native_executes_as_real_job_attempt_and_replays` integration fixture with `ORDIVON_RUN_WINDOWS_INTEGRATION=1`; it also exercises Runtime reconstruction and forced launcher death. The destructive distro-restart proof is the two-phase ignored `runtime_windows_native_wsl_restart_prepare_or_recover` fixture. Run Phase A with `ORDIVON_RUN_WINDOWS_WSL_RESTART_PHASE=prepare`, then launch `scripts/windows-wsl-restart-watchdog.ps1` from a detached Windows process against the emitted Windows-side manifest, and only after the distro/control plane returns run Phase B with `...=recover`. Phase B observes/reconciles the original Registry identity; it never admits a replacement effect.

### Bound ownership rule

A Runtime bound must name the invariant it protects. Public page-size limits are acceptable when a stable cursor provides complete continuation; chunk/tail limits are acceptable when offsets or explicit truncation flags preserve recoverability; transport-body and retained-byte ceilings protect control-plane/resource envelopes; identifier and filesystem constraints protect durable addressing; containment rules protect isolation. Representation cardinality by itself is not a reason to reject Agent work. Accordingly, Runtime does not impose bootstrap-era maxima on argv count, environment count, `execPlan` steps, foreign references, mutation count, Patch file/edit count, or cgroup budget values. Individual argv/environment strings and their combined payload remain subject to the host Linux `execve` physical limits (`MAX_ARG_STRLEN` and `_SC_ARG_MAX`).

## Maintenance reconciliation

The service performs a low-frequency bounded reconciliation batch in addition to startup reconciliation. The batch prioritizes recovery-required and held-orphaned Attempts, then inspects other unsettled Attempts oldest first. Missed timer ticks are skipped rather than queued, and one batch never exceeds the configured bound. Agent-facing projection reads (`workspace.get`, `workspace.list`, and `task.list`) do not run reconciliation. `task.observe(jobId)` is the explicit targeted reconciliation path for one Job, while execution admission may reconcile the same Workspace before admitting new work.

This loop does not redispatch ambiguous work or retry failed commands. It only continues convergence among Registry state, runner evidence, and systemd/cgroup reality, including clearing recovery markers that became stale after a conclusive terminal result.

## Semantic health and Workspace lifecycle

`ordivon-runtime-doctor inspect` remains read-only and reports invariant violations, recovery cases, state counts, capacity holders, Artifact volume, and whether the Runtime is `healthy` or needs `attention`. Its defensive 50-holder diagnostic projection reports `capacityHoldersTruncated=true` when incomplete rather than silently presenting a prefix as complete. The summary explains current blocking facts; it does not invent a second control plane.

`workspace.get` distinguishes immutable lineage from live Git state: `sourceRevision` is the exact commit from which the Workspace was opened, while `currentHeadRevision` is the commit currently checked out at Workspace HEAD. It also exposes `sourceStateDigest`, the existing commitment over current HEAD, index flags and entries, tracked source bytes, untracked source bytes, file modes, symlinks, and nested Git worktrees. `workspace.list` carries the same opening/current revision distinction, uses a lightweight Git status probe, stable newest-first cursor pagination, and omits the expensive `sourceStateDigest` by default; callers may set `includeSourceStateDigest=true` when one page really needs exact digests. Healthy Workspace records are never silently discarded by the page-size limit, and inventory/projection failures remain explicit `issues`. Both operations are projection-only and do not reconcile or dispatch Jobs. `workspace.close.expectedSourceStateDigest` performs compare-and-close while holding the Runtime lifecycle lock; active or held Jobs block closure directly from durable reservation state without being dispatched by the close attempt. The same critical section also protects open Workspace Git authority: before deleting a Workspace directory or its disposable cache/build/tmp paths, Runtime resolves the actual Git common directory of every other open Workspace and rejects the close with `WORKSPACE_BUSY` when one depends on a path about to be removed. Because `workspace.open` holds the same lifecycle lock, concurrent open/close cannot race past that dependency fence. A mismatch fails without removal, while a successful close stores the exact digest in the tombstone so the same request can be replayed after response loss. This is a physical source-state fence only: Host remains responsible for deciding which evidence authorizes semantic completion.

Capacity admission remains immediate rather than creating a hidden queue. The production global limit is configurable and set to eight; one Workspace still owns at most one active execution. A `CONCURRENCY_LIMIT` error carries bounded holder Job and Workspace identities so callers can observe the actual occupants instead of polling blindly. The repository-owned `ordivon-runtime-capacity-acceptance` command verifies this contract through MCP by admitting exactly the configured capacity, rejecting the next Job, checking holder identity, observing terminal success, and cleaning every temporary Workspace.

Runtime deployment uses one release-artifact authority for the service binaries and installed Runtime-owned operator executables/support module. `prepare` builds and stages from a temporary detached checkout of the requested Git Commit rather than trusting mutable working-tree cleanliness, so index flags cannot make an uncommitted byte masquerade as release source. The candidate/receipt binds the complete artifact set by digest and mode; `plan` treats local checkout HEAD/dirty state as diagnostics while the explicit required ref selects the releasable Commit. Apply and rollback move that artifact set together, and status verifies the installed set against the latest successful release-state event, including a later explicit rollback. A rollback inherits `previousCommit` only when the pre-deployment complete artifact fingerprint matched an earlier receipted release; otherwise the restored bytes and modes remain exact while the source Commit is explicitly unknown. Schema-v1 binary-only receipts remain rollback-readable without making them the current release model.

When `ORDIVON_RELEASE_SOURCE_REPO` configures operator-owned self-release authority, the MCP surface adds the first structured external-effect contract rather than teaching arbitrary execution about effects. `release.apply` binds the Agent's exact Commit/candidate-manifest expectation to a server-derived candidate directory, candidate deployer executable, install/Registry/environment/receipt authority, and a deterministic effect receipt. The binding is additive Job side truth and advances new release operations to `runtime-operation-v5` without changing historical Execution Plan JSON or Registry migration version. Exact replay occurs before current release-world checks. `release.get` is projection-only and treats the canonical deployment receipt as stronger evidence of external release occurrence than generic process state. Explicit rollback remains the existing operator action; Runtime does not infer that rollback is the Agent's strategy.

`ordivon-runtime-reclaim inspect` validates the Registry capabilities it actually reads instead of copying a migration-version ceiling. It may measure logical Workspace bytes and classify active, dirty, stale, orphan-directory, and closable cases. `ordivon-runtime-reclaim apply` remains the only release executor and can archive old `stale_record` identities or release old `closable` Workspaces only through `workspace.close`. `ordivon-runtime-lifecycle` adds configured `ephemeral`, `review`, and `pinned` retention classes, uses the latest durable Job/Attempt activity as the lease basis, and drives a receipted daily timer. Active, dirty, pinned, unknown, and orphan-directory cases are never automatic. Exact source-repository aliases can repair renamed Git worktrees; an explicitly confirmed quarantine path preserves unrepairable bytes and writes a closed tombstone. `workspace.close` removes that Workspace's disposable temporary, generic, Workspace-scoped compiled-build, and tmp caches before the physical worktree removal and tombstone commit, so a cleanup failure cannot be misreported after closure has committed. Global trusted-local package-download caches survive individual Workspace closure because they are reusable infrastructure rather than Workspace identity; legacy source-scoped build caches are migration/reclaim leftovers, not active execution targets. Deployment, lifecycle, hygiene, and rollback contracts are documented in [`operations.md`](operations.md).

## Completion and experience semantics

The Runtime uses five separate terms rather than one overloaded notion of completion:

- **Execution completion**: an Attempt has conclusive terminal execution evidence.
- **State convergence**: the Job has a resolution, every relevant Attempt is terminal, reservations are released, and no recovery condition remains active.
- **Client reattachment**: a caller reconnects to the same durable Job through its Job identity. Transport disconnects are not Attempt states.
- **Workspace closure**: the Git Workspace is independently proven closable and is removed through `workspace.close`, with rescue-ref and tombstone semantics.
- **Semantic completion**: an Agent or human concludes that the user's actual objective is satisfied. The Runtime does not adjudicate this claim.

A successful process exit is execution evidence, not proof of semantic completion. An Artifact is retained evidence, not proof that a claim is correct. A closed Workspace does not change Job resolution, and client reconnection does not change Attempt state.

## Mechanical acceleration measurements

`ordivon-runtime-inspect summary` derives mechanical latency distributions from the existing append-only Job event history. It reports admission-to-dispatch, dispatch-to-Runner binding, Runner-binding-to-terminal, cancellation-to-terminal, and reconciliation-failure-to-convergence intervals alongside total Job duration, recovery, duplicate-dispatch, cancellation, and Artifact facts. No timing table, telemetry service, or semantic score is added. Missing event pairs produce zero samples rather than invented timings. These measurements expose Runtime's physical contribution to a wider `verified improvement / unit time` evaluation; they do not decide whether the executed work was useful or correct.

## Correlated Job lookup

`task.list` retains newest-first cursor pagination and may additionally filter by an exact `workspaceId`, `clientRequestId`, or their intersection. The filters are projection-only reads over the durable Job Registry and indexed identities; `task.list` does not reconcile or dispatch Jobs and therefore cannot advance unrelated work as a side effect of reattachment. Recovery callers still consume every filtered page and reject conflicting Job identities rather than treating the newest match as sufficient proof. When the Agent needs fresher physical state, it targets one exact Job with `task.observe`, which may reconcile or dispatch that already-admitted Job but does not scan unrelated Jobs. The lookup indexes are maintained idempotently as non-semantic query capabilities rather than advancing the Registry schema version, so the previous Runtime binary can still open the same Registry during receipt-bound rollback.

There is intentionally no claim that `task.observe` is a pure read: it may advance reconciliation for the targeted durable Job. `task.get` is the exact non-reconciling `jobId` projection and reuses Runtime Core's read-only inspection truth rather than duplicating Job query semantics in MCP. Its public timeline is bounded by `eventLimit`, omits unbounded event detail, and leaves retained stdout/stderr/results behind `artifact.read`; operator-local inspection may still request forensic event detail. `task.list` remains the paginated non-reconciling discovery/reattachment projection when the exact Job identity is not yet known.

## Read-only experience projection

The append-only Runtime Registry remains the only physical execution-fact database for Runtime Jobs and Attempts. `ordivon-runtime-inspect` derives bounded reports without adding tables, events, or a second history store:

```text
ordivon-runtime-inspect job --database <registry> --job-id <job> --pretty
ordivon-runtime-inspect workspace --database <registry> --store-root <runtime-store> --workspace-id <workspace> --pretty
ordivon-runtime-inspect summary --database <registry> --since-ms <unix-ms> --pretty
```

The Job report projects Attempts, reservations, conditions, Artifact volume, recovery/cancellation episodes, and a bounded event timeline. The Workspace report combines current Git HEAD/status with complete active-Job identities and a bounded recent-Job projection including Attempt state, execution disposition, recovery requirement, duration, Runner progress/current step, last output activity, and Artifact count. Each Registry-backed inspection holds one query-only SQLite read snapshot so concurrent Job transitions cannot fabricate cross-query inconsistencies; Git and filesystem facts remain separate physical observations rather than pretending to be one cross-owner transaction. Inspection never calls `task.observe` or reconciliation. The summary reports mechanical convergence, resolutions, recovery convergence, duplicate physical dispatch, cancellation outcomes, duration percentiles, Artifact volume, and terminal reasons. None of these reports evaluates semantic completion.

These metrics are diagnostic references for Runtime changes. They do not score model reasoning, user satisfaction, context quality, or user rework, and they do not create a new MCP tool.

## MCP protocol boundary

The Adapter uses the stable MCP `2026-07-28` stateless lifecycle as its canonical path and currently retains compatibility lifecycles `2025-11-25` and `2025-06-18` on the same HTTP endpoint. Modern requests use `server/discover`, standard routing headers, and per-request metadata without a protocol Session. `LocalSessionManager` exists only for legacy `initialize` clients; Runtime continuity remains the durable Workspace/Job/Attempt model in Core.

The MCP HTTP request body remains bounded to `ORDIVON_BODY_LIMIT_BYTES` (1 MiB in production). This is a control-plane envelope, not a large-object transport: scalar arguments remain inline, while future source replacements above that envelope require digest-bound Artifact or stdin input rather than larger argv values or an unbounded HTTP body.

Omitting `waitMs` on public execution admission performs only a brief 2-second observation after the durable Job exists; explicit callers may still request longer waits up to the existing Core maximum. This keeps the normal MCP request lifecycle shorter than long-running execution while preserving the same durable Job/Attempt identity for later `task.observe`. systemd launch/cancel commands are submitted with `--no-block` after the corresponding Runtime intent is durable; Runner launch evidence, process identity, terminal evidence, and reconciliation remain physical truth.

Workspace reads distinguish response bounds from proof cost. FULL reads hard-cap bytes actually consumed. SLICE reads keep memory proportional to the requested slice plus a fixed streaming buffer while still validating and hashing the whole file in one pass; therefore SLICE I/O remains O(file size) because the public result still includes a whole-file digest. `workspace.diff.maxBytes` is narrower: it bounds retained diff text, and Runtime now stops the Git child after observing one byte beyond that budget instead of materializing complete diff stdout first. Its historical structured changed/modified/added/deleted/renamed/untracked arrays remain complete and therefore are intentionally not response-bounded.

`workspace.changes` is the response-bounded structured surface for large change sets, and Runtime retains only a bounded candidate/page set while producing it. Each page returns one atomic entry stream (`modified`, `added`, `deleted`, or `untracked`), with `limit` bounding entry count and `maxBytes` bounding the encoded entry payload. Runtime asks Git for exact path/kind truth, derives an order-independent `changeSetDigest`, orders continuation by the canonical `(path, kind)` order rather than Git emission order, and returns `nextCursor={changeSetDigest, afterPath, afterKind}` when more entries remain. The cursor is valid only while the projected change membership/kinds are unchanged, and `afterPath`/`afterKind` must name a real member of that set. Byte changes inside an already-`modified` or already-`untracked` path intentionally do not invalidate continuation because this Tool proves the structured change set rather than source bytes; callers that require exact byte identity use `workspace.get.sourceStateDigest` or file digests.

Rename/copy similarity detection is intentionally disabled on this scalable projection: a rename is represented as one deleted path plus one added path. `workspace.diff` remains the richer compatibility surface when rename interpretation is worth its extra Git analysis cost. Git's exhaustive rename/copy fallback can become quadratic in the number of unmatched sources/destinations, which is the wrong hidden default for the large-change-set path.

The Tool does not claim O(page) discovery work. Without a separate maintained change index or snapshot, Git must still enumerate the current change metadata to establish the page and its continuation fingerprint; Runtime performs a second exact change-set scan to reject a transition during one page projection. Work is therefore O(current change count) per page while response size and Runtime-owned retained entry memory remain bounded. Exact Git change detection may still read changed file bytes and the Git child process's I/O/RSS can scale with changed file size; `maxBytes` is not a Git resource budget. The public MCP default remains 64 entries, while callers may raise `limit` up to 1024 under the same `maxBytes` response budget after inspecting `totalEntries` and `remainingEntries`. A persistent change/content index would create a new state owner and is not justified until real workloads show that discovery cost, rather than response size, is the bottleneck.

Executable identity also separates invocation semantics from target authority. Runtime requires an absolute invocation path, requires both the invocation location and canonical target to remain inside configured executable roots, validates the target SHA-256, persists the invocation path, and Runner executes the verified target with the original invocation restored as `argv[0]`. This preserves rustup-style multicall/proxy behavior without allowing a symlink retarget to bypass executable verification.

`server/discover` returns a deterministic SHA-256 `toolCatalogDigest` over the complete name-sorted Tool definitions with `ttlMs=0` and private cache scope. Deployment receipts bind this digest. Every public Tool publishes both its generated input schema and a structured `outputSchema`; the output contract is the union of the exact success result and the standard `{ "error": ToolError }` envelope, whose `origin`, `retryClass`, and `commitState` values are finite machine-readable vocabularies. `workspace.exec` exposes Core's typed execution proposal directly: MCP decides only whether an all-explicit legacy request must preserve its v1 identity shape or whether the request uses proposal semantics. `workspace.execBound` is a separate versioned admission Tool: it adds exact named-authority input commitments, fixes the profile to `contained_local`, and uses its own proposal-plus-input request identity while reusing the same Job/Attempt/Artifact lifecycle. Operator authority roots come from `ORDIVON_INPUT_AUTHORITIES_JSON`; callers never submit host source paths. Core owns proposal canonicalization, policy resolution, idempotent replay, materialization, and effective-plan truth. The Adapter no longer advertises or implements the experimental Core Tasks methods (`tasks/list`, enqueue, get, result, cancel). Execution Tools return Ordivon Job observations, while `task.observe`, `task.list`, and `task.cancel` remain ordinary Tools. MCP adapts transport and discovery; it does not become Runtime's persistence model.

Runtime trace JSONL files rotate at 64 MiB and retain one previous segment. Rotation and append are serialized by one process-local mutex so concurrent MCP requests cannot race the rename/open sequence. `scripts/ordivon-runtime-status` scans the current and rotated segments within its existing bounded byte budget, and projects a compatibility inventory from the current deployment receipt, recent protocol observations, and the immediately previous receipted deployment. Every retained protocol version therefore names a current production, live-client, or rollback consumer plus a deletion trigger. Missing, truncated, or not-yet-long-enough trace evidence blocks deletion conclusions but does not make Runtime unhealthy. The complete inventory, including persisted-state compatibility, is defined in [`compatibility.md`](compatibility.md).

## Verification

The architecture is verified by the canonical Runtime test suite, migration and Registry checks, generated MCP schemas, deployment receipts, capacity acceptance, recovery inspection, and identity-bound terminal evidence. ## Extension boundary

Use existing host executables through `workspace.exec` unless repeated real use proves that a stable operation needs a dedicated structured Tool contract. Arbitrary execution is effect-opaque and may interact with an open world of external entities: a caller may not promote it to read-only, idempotent, closed-world, or reconcilable by declaration. A structured effect adapter is justified only when it owns canonical identity, enforceable preconditions, receipt or state proof, reconciliation, and ambiguity behavior. `contained_local` reduces ambient local authority for ordinary engineering workloads; genuinely hostile, multi-tenant, controlled-egress, or disposable workloads still require an external isolation boundary owned outside Runtime.
