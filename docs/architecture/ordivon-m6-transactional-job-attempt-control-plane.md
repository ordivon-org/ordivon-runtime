# Ordivon M6 Transactional Job and Attempt Control Plane

- Status: design freeze only
- Branch: `agent/m6-transactional-job-attempt-control-plane`
- Base: `1c7293cbb74f9662a47d80bc0fe91ce4b5b020fd`
- Date: 2026-07-22
- Production status: not implemented, deployed, or routed

## 1. Purpose

M1–M5 proved a durable local Runner, compact Agent interface, real MCP adapter,
and bounded Dogfood. They did not provide an atomic control-plane truth for
idempotency, concurrency, Job/Attempt separation, crash recovery, retention,
or list operations.

M6 introduces a feature-gated SQLite control plane while retaining the existing
systemd/cgroup Runner and filesystem Artifacts.

The central object model is:

```text
MCP Task = protocol projection of Job
Job      = stable intent and idempotency boundary
Attempt  = one concrete dispatch and execution lifecycle
Runner   = one systemd/cgroup process tree
Artifact = immutable evidence produced by one Attempt
```

## 2. Observed baseline

The current Universal Executor persists each Task in:

```text
store/tasks/<taskId>/
  request.json
  metadata.json
  stdout.log
  stderr.log
  result.json
```

Task creation uses directory existence as uniqueness. Concurrency policy is
evaluated from caller-supplied snapshots rather than atomically reserved.
Task status reads `result.json` first and then queries systemd. Cancellation
writes `cancel.json`, calls `systemctl stop`, and may write a terminal result.

The earlier Job contract already defines authority, Capability Policy,
ExecutionPlan, lifecycle states, output cursors, operational events, and a pure
supervisor recovery classifier. It currently combines stable Job identity and
one concrete execution in one `JobRecord`.

M6 must merge these two lines. It must not create a third parallel Task truth.

## 3. Scope and non-goals

M6 includes:

- SQLite schema and versioned migrations;
- server-generated Job and Attempt identifiers;
- idempotency binding;
- global and profile concurrency reservations;
- immutable execution-plan snapshots;
- atomic Job, Attempt, event, reservation, and Artifact metadata transitions;
- startup, periodic, and targeted reconciliation;
- bounded Job listing and status projection;
- compatibility projection to MCP Tasks;
- crash-window and concurrent-access evidence.

M6 does not include:

- production port 8811 routing;
- Cloudflare, OAuth, or remote exposure;
- Git push, merge, deployment, or external side effects;
- network or credential delegation;
- a dedicated non-root Worker, which remains M7;
- automatic retry after ambiguous dispatch;
- multi-node scheduling, Kubernetes, Nomad, or Temporal reimplementation;
- Tool Foundry promotion.

## 4. Non-negotiable invariants

1. Job IDs and Attempt IDs are generated by Ordivon, not selected by clients.
2. `(principal, clientRequestId)` is the idempotency key.
3. The same idempotency key and operation digest returns the existing Job.
4. The same idempotency key with a different digest returns
   `IDEMPOTENCY_CONFLICT` and never dispatches.
5. Attempt terminal states never reopen.
6. Job resolution, once present, is immutable.
7. Retry, when later enabled, creates a new Attempt and never reuses an old one.
8. No external process launch occurs before a committed Attempt exists.
9. An ambiguous dispatch is never automatically repeated.
10. State mutation, event append, reservation change, and Artifact registration
    that represent one observation occur in one database transaction.
11. Runner result files are mechanical evidence; systemd is lifecycle evidence;
    SQLite is control-plane truth. None substitutes for all three.
12. MCP Session state is never required to recover a Job.
13. Orphaned Attempts continue consuming capacity until explicitly remediated.
14. Lost Attempts release capacity only when no live process identity is proven.
15. Database corruption, result corruption, and identity mismatch fail closed.
16. M6 remains feature-gated and cannot change production routing.

## 5. Storage decision

M6 uses one local SQLite database under the feature-gated M6 store. The first
implementation should use a synchronous Rust SQLite adapter because
`ordivon-exec` is currently synchronous and state transitions are short.
The exact crate and version are locked during M6.0 dependency review.

Required database settings:

```text
PRAGMA foreign_keys = ON
PRAGMA journal_mode = WAL
PRAGMA synchronous = FULL
PRAGMA busy_timeout = 5000
PRAGMA trusted_schema = OFF
```

The database must reside on a local filesystem. WAL mode is not supported as a
shared multi-host database and M6 makes no network-filesystem claim.

Every write path begins with `BEGIN IMMEDIATE`. This acquires the SQLite write
transaction before validation based on mutable registry state and prevents a
mid-transaction upgrade from unexpectedly failing after partial logical work.
A bounded busy timeout returns a retryable `REGISTRY_BUSY`; it never waits
indefinitely.

Database and parent-directory permissions are `0600` and `0700`. Startup runs
migration checksum validation, `foreign_key_check`, and a bounded quick check.

## 6. Registry schema

### 6.1 `schema_migrations`

```text
version INTEGER PRIMARY KEY
name TEXT NOT NULL
checksum TEXT NOT NULL
applied_at_ms INTEGER NOT NULL
```

Migrations are ordered, checksum-bound, and forward-only. An unknown newer
schema fails closed. M6 does not auto-downgrade.

### 6.2 `idempotency_keys`

```text
principal TEXT NOT NULL
client_request_id TEXT NOT NULL
operation_digest TEXT NOT NULL
job_id TEXT NOT NULL
created_at_ms INTEGER NOT NULL
PRIMARY KEY (principal, client_request_id)
UNIQUE (job_id)
```

The operation digest binds the canonical request, workspace snapshot,
Capability/authority snapshot, and resolved execution-plan digest. Reusing the
key after a policy change therefore returns the original Job or conflicts; it
never silently creates a differently authorized execution.

### 6.3 `jobs`

```text
job_id TEXT PRIMARY KEY
principal TEXT NOT NULL
client_request_id TEXT NOT NULL
request_digest TEXT NOT NULL
operation_digest TEXT NOT NULL
workspace_id TEXT NOT NULL
workspace_snapshot_json TEXT NOT NULL
plan_kind TEXT NOT NULL
execution_plan_json TEXT NOT NULL
execution_plan_digest TEXT NOT NULL
policy_id TEXT NOT NULL
policy_version TEXT NOT NULL
policy_digest TEXT NOT NULL
authority_ref TEXT NOT NULL
profile_id TEXT
created_at_ms INTEGER NOT NULL
desired_state TEXT NOT NULL
resolution TEXT
current_attempt_id TEXT
row_version INTEGER NOT NULL
```

`desired_state` initially supports `run` and `cancelled`. `resolution` is
nullable until the Job is irreversibly resolved as succeeded, failed,
cancelled, lost, or orphaned.

The Job owns stable intent and authorization identity. It does not own a PID,
systemd unit, output counters, or exit code.

### 6.4 `attempts`

```text
attempt_id TEXT PRIMARY KEY
job_id TEXT NOT NULL
attempt_number INTEGER NOT NULL
state TEXT NOT NULL
termination_intent TEXT NOT NULL
launch_token_digest TEXT NOT NULL
bundle_path TEXT NOT NULL
bundle_digest TEXT
boot_id TEXT
unit_name TEXT NOT NULL
invocation_id TEXT
control_group TEXT
main_pid INTEGER
process_start_identity TEXT
runner_start_digest TEXT
result_digest TEXT
exit_code INTEGER
infrastructure_error_digest TEXT
created_at_ms INTEGER NOT NULL
started_at_ms INTEGER
finished_at_ms INTEGER
row_version INTEGER NOT NULL
UNIQUE (job_id, attempt_number)
```

Attempt state reuses the existing lifecycle semantics:

```text
accepted → starting → running → stopping / recovering → terminal
```

The existing `JobInternalState` contract is semantically execution-attempt
state. M6 should introduce `AttemptState` and retain a compatibility alias only
while older tests and schemas migrate.

Unit names are deterministic from Attempt IDs. A random launch token is stored
as a digest in SQLite, included in the immutable runner bundle, and emitted in
the runner-start evidence. This allows recovery to bind a newly observed unit
to the committed Attempt without trusting unit name alone.

### 6.5 `concurrency_reservations`

```text
reservation_id TEXT PRIMARY KEY
attempt_id TEXT NOT NULL UNIQUE
profile_id TEXT
global_limit INTEGER NOT NULL
profile_limit INTEGER
state TEXT NOT NULL
acquired_at_ms INTEGER NOT NULL
released_at_ms INTEGER
release_reason TEXT
```

Active reservations are counted inside the same `BEGIN IMMEDIATE` transaction
that creates an Attempt. There is no time-based lease expiry in M6: a slow Job
must not lose authority because a clock-based lease elapsed.

Terminal succeeded, failed, timed-out, cancelled, and provably lost Attempts
release their reservation. Orphaned Attempts keep a `held_orphaned`
reservation until explicit remediation proves the process tree is gone.

### 6.6 `job_events`

```text
event_id TEXT PRIMARY KEY
job_id TEXT NOT NULL
attempt_id TEXT
event_sequence INTEGER NOT NULL
event_type TEXT NOT NULL
origin TEXT NOT NULL
previous_state TEXT
new_state TEXT
reason_code TEXT NOT NULL
detail_json TEXT NOT NULL
detail_digest TEXT NOT NULL
observed_at_ms INTEGER NOT NULL
UNIQUE (job_id, event_sequence)
```

Events are append-only evidence written in the same transaction as the current
state mutation. M6 is not a fully event-sourced system: current Job and Attempt
rows are authoritative projections, while events make transitions auditable
and independently checkable.

### 6.7 `artifacts`

```text
artifact_id TEXT PRIMARY KEY
job_id TEXT NOT NULL
attempt_id TEXT NOT NULL
kind TEXT NOT NULL
relative_path TEXT NOT NULL
digest TEXT NOT NULL
media_type TEXT NOT NULL
byte_length INTEGER NOT NULL
truncated INTEGER NOT NULL
created_at_ms INTEGER NOT NULL
UNIQUE (attempt_id, kind, relative_path)
```

Artifact bytes remain in the attempt directory. SQLite stores identity,
lineage, digest, bounds, and location. Terminal Attempt transition and Artifact
registration occur in one transaction after the result bundle has been
validated.

### 6.8 `attempt_conditions`

This table is a rebuildable current view, not independent truth:

```text
attempt_id TEXT NOT NULL
condition_type TEXT NOT NULL
status TEXT NOT NULL
reason_code TEXT NOT NULL
evidence_digest TEXT NOT NULL
observed_at_ms INTEGER NOT NULL
PRIMARY KEY (attempt_id, condition_type)
```

Initial condition types are `bundle_ready`, `dispatch_issued`, `runner_bound`,
`result_available`, `recovery_required`, and `reservation_held`.

## 7. Execution plan classes

M6 preserves both classical and Agentive execution without merging their
authority models.

### 7.1 `governed_profile`

A public request selects a versioned profile. Existing Capability Policy code
resolves an immutable `ExecutionPlan` with executable, digest, exact argv, CWD,
environment, limits, principal, authority, and policy identity.

### 7.2 `universal_sandbox`

The model may author a program in an admitted workspace and choose an
interpreter or toolchain within a versioned Universal Sandbox Policy. The
policy freezes executable roots, workspace scope, environment rules, network
off, credential paths inaccessible, resource ceilings, and forbidden external
side effects.

Both classes resolve to a canonical execution-plan envelope and digest before
registry admission. Raw MCP data is never stored as an executable plan.

The M4/M5 raw `UniversalExecRequest` remains available only on the older
experimental feature during migration. The M6 transactional path requires a
server-generated Job ID and a client-provided `clientRequestId`.

## 8. Submit transaction

Expensive immutable validation occurs before the write transaction:

```text
validate request shape
→ load and validate policy
→ canonicalize workspace snapshot
→ resolve execution plan
→ compute request, plan, and operation digests
→ generate Job ID, Attempt ID, and launch token
```

The atomic admission transaction is:

```text
BEGIN IMMEDIATE
→ lookup (principal, clientRequestId)
→ same digest: return existing Job without a launch
→ different digest: IDEMPOTENCY_CONFLICT
→ count active global and profile reservations
→ deny with retryable CONCURRENCY_LIMIT if full
→ insert idempotency key
→ insert Job
→ insert Attempt in accepted state
→ insert active concurrency reservation
→ append REQUEST_RECEIVED, AUTHORIZATION_ALLOWED,
  JOB_RECORD_CREATED, and ATTEMPT_CREATED events
→ set Job.currentAttemptId
COMMIT
```

No filesystem bundle or process is created before this commit. A committed
accepted Attempt is durable work for the dispatcher and reconciler.

## 9. Dispatch protocol

The dispatcher handles committed `accepted` Attempts.

### 9.1 Bundle materialization

The immutable plan stored in SQLite is rendered to:

```text
store/attempts/<attemptId>/
  request.json
  plan.json
  bundle-manifest.json
  runner-start.json
  stdout.log
  stderr.log
  result.json
```

Files are written to a staging directory, fsynced, and atomically renamed.
Bundle identity is written back to SQLite with a `bundle_ready` condition.
Bundle materialization is derived and repeatable before dispatch.

### 9.2 Dispatch intent

Before invoking systemd, one transaction changes the Attempt from `accepted`
to `starting`, records `dispatch_issued`, appends an event, and increments
`row_version`. This is the at-most-once dispatch boundary.

After commit, the dispatcher invokes systemd using a deterministic unit name,
the Attempt bundle path, and the launch token. It then reads systemd and
`runner-start.json`, validates the launch token, InvocationID, cgroup, PID,
process start identity, and boot ID, and transactionally moves the Attempt to
`running`.

### 9.3 Ambiguous dispatch policy

SQLite and systemd cannot participate in one atomic transaction. Therefore a
crash can occur after `dispatch_issued` but before Ordivon records the running
identity.

M6 chooses at-most-once dispatch under uncertainty:

- if the deterministic unit, runner-start evidence, or result proves the
  committed launch token, reconciliation binds or finalizes the same Attempt;
- if no matching evidence exists after an issued dispatch, the Attempt becomes
  `lost` with reason `DISPATCH_OUTCOME_UNKNOWN`;
- M6 never automatically launches that Attempt again;
- an explicit retry, when later enabled, creates a new Attempt ID.

This may produce a false `lost` outcome after a crash that occurred before the
systemd call, but it prevents silent duplicate program execution. That tradeoff
is required because even mature Job controllers can start a program more than
once, so workloads with side effects must remain idempotent or reconciled.

## 10. Terminal commit

The Runner remains intentionally simple. It drains output, writes bounded log
files, writes `runner-start.json`, and atomically writes `result.json`. It does
not write SQLite.

Core or the reconciler validates the result identity, output digests, bounds,
launch token, Attempt ID, and Job ID. It then performs one transaction:

```text
BEGIN IMMEDIATE
→ verify Attempt row_version and non-terminal state
→ update Attempt terminal state and result fields
→ register stdout, stderr, and result Artifacts
→ release or retain concurrency reservation according to outcome
→ set immutable Job resolution
→ clear Job.currentAttemptId
→ append PROCESS_EXITED, JOB_TERMINAL, and reservation events
COMMIT
```

If another observer already committed the same validated result, the operation
returns the existing terminal projection. A different result digest is
`RESULT_IDENTITY_CONFLICT` and fails closed.

## 11. Cancellation protocol

Cancellation is intent-first and idempotent:

```text
BEGIN IMMEDIATE
→ terminal Job: return existing projection
→ set Job.desiredState = cancelled
→ set Attempt.terminationIntent = stop_requested
→ running/starting Attempt → stopping
→ append STOP_REQUESTED event
COMMIT
→ issue systemctl stop outside the transaction
```

Repeated stop calls are safe. Startup and periodic reconciliation reissue stop
for `desiredState=cancelled` Attempts that still have a matching live unit.
Final cancellation is committed only after result or supervisor evidence proves
the process tree is gone.

## 12. Reconciliation model

M6 runs reconciliation:

1. synchronously on server startup before accepting new writes;
2. periodically for non-terminal Attempts;
3. on targeted Job observation when state may be stale.

Reconciliation reads SQLite first, then bounded filesystem, systemd, procfs,
cgroup, and boot-ID evidence. The existing pure supervisor classifier remains
the classification kernel.

Reconciliation never treats absence of evidence as success. It may:

- recreate a missing bundle only while Attempt state is `accepted`;
- bind a `starting` Attempt only when launch-token evidence matches;
- update `running`, `stopping`, or `recovering` from matching supervisor identity;
- commit a validated runner result;
- mark changed-boot, missing-unit, no-result Attempts as lost;
- mark identity mismatch or live process without unit as orphaned;
- quarantine corrupt result or metadata as orphaned with a corruption reason;
- release reservations only when process absence is proven or cancellation has
  is terminal and process absence is proven.

## 13. Mandatory crash-window matrix

| Crash point | Required recovery |
|---|---|
| before admission commit | no Job, Attempt, reservation, or launch |
| after Job commit, before bundle | rebuild bundle from immutable plan |
| during staging bundle write | delete staging data and rebuild |
| after bundle, before dispatch intent | resume dispatch safely |
| after dispatch intent, before systemd call | no evidence → lost; never auto-repeat |
| after systemd launch, before identity commit | bind only with matching launch token |
| Runner starts, Core unavailable | Runner continues and writes result |
| result written, DB non-terminal | validate result and commit terminal state |
| DB terminal transaction interrupted | transaction rolls back; reconciliation retries |
| stop intent committed, systemctl not issued | reconciliation reissues stop |
| process gone, reservation still active | terminal reconciliation releases reservation |
| unit missing, matching PID alive | orphaned; reservation remains held |
| boot ID changed, no result | lost; reservation releases |
| corrupt result | fail closed as orphaned/corrupt; no fabricated result |
| duplicate terminal observer | same digest is idempotent; different digest conflicts |
| WAL or database unavailable | reject writes; never fall back to file-only mutation |

Each row requires an automated test. At least the dispatch ambiguity, terminal
commit, cancellation, boot change, duplicate observer, and reservation release
cases require real systemd integration evidence in addition to pure tests.

## 14. MCP and Task projection

M6 does not add a second public Job protocol. The existing MCP Task surface
projects one Job:

```text
MCP taskId        = server-generated Job ID
Task status       = Job resolution or current Attempt projection
Task result       = terminal Job resolution plus current/final Attempt Artifacts
Task cancellation = persisted Job desired-state change
Task list         = bounded Job list ordered by createdAt + Job ID
```

`workspace.exec` on the M6 feature requires `clientRequestId` and no longer
accepts a client-selected durable Task ID. It returns the generated Job ID.
Native MCP Tasks and explicit `task.observe` compatibility calls use the same
Job row.

Artifact IDs are Attempt-qualified internally. The compact Job projection may
expose final Attempt Artifacts without repeating Attempt metadata; diagnostic
projection includes Job ID, Attempt ID, attempt number, policy digest,
reservation state, and reconciliation evidence.

The M4/M5 adapter remains available as a comparison backend until M6 evidence
passes. There is no silent migration or fallback between file and SQLite truth.

## 15. Migration boundary

M6 uses a separate feature and database path. Existing M1–M5 `tasks/`
directories remain historical experimental evidence and are not imported as
live Jobs.

The migration strategy keeps the M4/M5 file-backed Adapter unchanged as the
comparison baseline. M6 registry types and migrations are added behind the
`transactional-registry-m6` feature and use a separate local port and store.
New local Jobs may use the M6 path only after its evidence gates pass. Old Tasks
remain readable through the M4/M5 diagnostic path until a later retention
decision. There is no silent fallback between file and SQLite truth.

A future historical importer may index terminal old Tasks as legacy evidence,
but it must never infer missing authority, idempotency, or Attempt identity.
That importer is not part of M6.

Workspace creation remains outside the SQLite lifecycle in M6. Admission stores
an immutable canonical workspace snapshot. Transactional workspace ownership
would be a separate scope increase.

## 16. Delivery plan

### M6.0 — Contract and SQLite spike

Freeze schema, migration checksums, identifier format, SQLite adapter choice,
connection settings, error taxonomy, and deterministic test fixtures.

Deliverables:

- schema migration files;
- pure schema and constraint tests;
- `BEGIN IMMEDIATE` busy/conflict spike;
- corrupt/newer-schema fail-closed tests;
- no Runner or MCP routing changes.

Exit gate: two concurrent writers cannot both claim one idempotency key or the
last available reservation.

### M6.1 — Registry core

Implement Job, Attempt, idempotency, events, reservations, Artifact metadata,
and bounded list/read repositories. No process launch yet.
### M6.2 — Transactional admission and dispatch

Connect Capability evaluation to the registry, create immutable bundles, add
launch tokens, and dispatch the existing Runner. Add no automatic retry.

Exit gate: repeated same-key submission returns the same Job and produces one
Attempt and at most one dispatch intent; changed input conflicts.

### M6.3 — Terminal and cancellation transactions

Register result and output Artifacts, resolve Jobs, release reservations, and
make cancellation intent-first and recoverable.

Exit gate: concurrent terminal observers produce one terminal transition and
one Artifact set; concurrent stop requests remain idempotent.

### M6.4 — Reconciler and crash matrix

Implement startup, periodic, and targeted reconciliation using the existing
supervisor classifier and new launch-token evidence.

Exit gate: every mandatory crash-window row has automated evidence and no case
silently redispatches an ambiguous Attempt.
### M6.5 — MCP compatibility bridge

Project Jobs through Native MCP Tasks and explicit Task compatibility tools on
a new experimental port. M4/M5 remains the Shadow baseline.

Exit gate: Server restart, duplicate submit, list pagination, cancellation, and
Artifact retrieval all use SQLite Job truth and survive MCP Session loss.

### M6.6 — Evaluation and decision

Run:

- the M5 scripted journey matrix;
- 2/4/8 concurrent admission and execution;
- crash and recovery journeys;
- at least one bounded model-in-the-loop read/edit/test/repair task;
- M5 file backend versus M6 registry backend Shadow comparison.

The final decision may authorize continued local M6 Dogfood only. Production
routing remains a separate decision after M7 worker hardening.

## 17. Error taxonomy additions

M6 adds stable errors without replacing existing Job errors:

```text
REGISTRY_UNAVAILABLE
REGISTRY_BUSY
REGISTRY_CORRUPT
SCHEMA_VERSION_UNSUPPORTED
MIGRATION_CHECKSUM_MISMATCH
IDEMPOTENCY_CONFLICT
CONCURRENCY_LIMIT
JOB_NOT_FOUND
ATTEMPT_NOT_FOUND
ATTEMPT_STATE_CONFLICT
JOB_ALREADY_RESOLVED
RESULT_IDENTITY_CONFLICT
DISPATCH_OUTCOME_UNKNOWN
LAUNCH_IDENTITY_MISMATCH
RESERVATION_STATE_CONFLICT
ARTIFACT_IDENTITY_CONFLICT
RECONCILIATION_REQUIRED
```

Retryability is explicit. Registry busy and concurrency limit are retryable.
Identity conflict, corrupt metadata, unsupported schema, and ambiguous dispatch
are not automatically retryable.

## 18. Performance requirements

M6 adds control-plane durability but must not make short transactions expensive.
Registry timing is measured separately from process runtime.
Required initial budgets on the reference WSL environment:

```text
idempotent replay lookup p95       ≤ 20 ms
new Job admission transaction p95  ≤ 50 ms
status read without reconcile p95  ≤ 20 ms
bounded list of 100 Jobs p95       ≤ 50 ms
terminal commit p95                ≤ 50 ms
```

These are registry-only budgets and exclude policy file loading, Git workspace
creation, systemd launch, and target runtime. If the environment cannot meet a
budget, evidence must separate SQLite time, filesystem time, and OS-supervisor
time before changing the threshold.

M6 must retain the M5 Agent-facing budgets for equivalent journeys. Extra
Job/Attempt identity belongs in diagnostic projection, not default compact
responses.

## 19. Test and evidence gates

Required pure and database tests:

- schema, foreign keys, CHECK constraints, and migration checksums;
- idempotent replay and conflict;
- global/profile reservation races;
- row-version and state-transition conflicts;
- event sequencing and append-only behavior;
- terminal Job and Attempt immutability;
- bounded list cursors;
- Artifact lineage and digest conflict;
- database busy, corrupt, missing, and newer-schema behavior.
Required real integration evidence:

- duplicate simultaneous submissions produce one Job and one Attempt;
- concurrent admissions never exceed global or profile limits;
- Server exits after admission and a later Server dispatches accepted work;
- Server dies during dispatch and reconciliation does not duplicate execution;
- result is committed after Core absence;
- cancellation survives Core restart;
- changed boot ID produces lost rather than running;
- identity mismatch produces orphaned and keeps capacity reserved;
- no residual units, processes, worktrees, reservations, or staging bundles;
- M5 journeys remain semantically equivalent.

Evidence must contain raw observations and an independent checker. At least one
summary field must be tamper-tested.

## 20. Mature-system alignment

M6 borrows only the minimum proven patterns:

- SQLite transactions provide one local atomic writer and durable relational
  constraints; `BEGIN IMMEDIATE` makes write contention explicit early.
- Temporal motivates durable intent and recovery from persisted history, but
  M6 does not implement deterministic workflow replay.
- Nomad motivates separation of desired Job, evaluation/reconciliation, and
  concrete allocation; M6 maps these to Job, reconciler decision, and Attempt.
- Kubernetes demonstrates that a Job program may be started more than once;
  M6 therefore treats ambiguous dispatch as lost instead of auto-repeating it.

Ordivon's distinctive layer remains the combination of local workspace,
Agent-authored programs, capability snapshots, compact MCP projection, and
user-owned execution evidence.

## 21. Resolved and deferred decisions

Resolved for M6:

- SQLite is the local control-plane database.
- Job and Attempt are separate persisted objects.
- MCP Task projects Job, not Attempt.
- clientRequestId is the idempotency key component; Job IDs are server-generated.
- writes use `BEGIN IMMEDIATE` and bounded busy handling.
- dispatch is at-most-once under uncertainty.
- Runner files remain evidence and are not replaced by database blobs.
- orphaned capacity remains reserved until explicit remediation.
- no automatic retry is exposed in M6.

Deferred:

- exact Rust SQLite crate version, locked in M6.0;
- UUIDv7 library choice, also locked in M6.0;
- long-term historical import of M1–M5 Tasks;
- transactional workspace ownership;
- non-root Worker identity;
- remote and external-side-effect authority.

## 22. Immediate next action

The first implementation step is M6.0 only: add migration files, a feature-
gated Registry adapter, identifier types, SQLite configuration validation, and
concurrent idempotency/reservation tests. It must not launch a process, expose a
new MCP tool, or alter the M4/M5 adapter.
